ESP32 能量罐

手勢辨識出技能後，要先向 ESP32 申請能量，獲准才送到競技場。這頁整理了這次的實作、變更檔案和測試方式。

尚未在實體硬體上測試 分支 feat/esp32-energy-can 競技場伺服器不需修改
預設容量 6 · 每 2 秒 +1
運作方式

技能送出前多一道關卡

能量判斷放在玩家電腦上的 Python 辨識器裡，夾在 Pipeline.predict() 和 ArenaClient.send() 之間。ESP32 拒絕的技能，該通道會改送 NONE；移動、格擋這類動作照常送出。競技場原本的氣量、冷卻和硬直規則都保留，兩邊都通過才會施放。

sequenceDiagram
    participant P as 手勢辨識 predict()
    participant G as EnergyGate
    participant E as ESP32 能量罐
    participant A as 競技場
    P->>G: Commands(right=ULTIMATE)
    G->>E: REQ 7 ULTIMATE
    alt 能量足夠
        E-->>G: OK 7 3
        G->>A: input:state ULTIMATE
        A-->>G: input:result reason
        opt reason 不是 OK（冷卻、氣量不足…）
            G->>E: REFUND 7
            E-->>G: REFUNDED 7 6
        end
    else 能量不足
        E-->>G: NO 7 2
        G->>A: input:state NONE
    end

每按一次只問一次

手勢維持期間沿用同一個結果。離開 0.12 秒才算放開，對應競技場離開 6 tick 才重新觸發的規則，辨識閃爍不會重複扣能量。

沒施放就退回

競技場回報 COOLDOWN、INSUFFICIENT_QI、ULTIMATE_LOCKED 等失敗，或 1.5 秒內沒有施放結果，會自動送 REFUND。

沒回應就擋下

ESP32 0.15 秒內沒回覆或斷線時，技能一律擋下。加 --energy-fail-open 改為放行。

不接就不影響

沒有加 --energy-port 時完全不使用能量罐，行為和原本相同。

序列協定 · 115200 baud · ASCII 行

PC 和 ESP32 之間的對話

<id> 是 Python 端遞增的整數，回覆用 id 對應請求。不認得的行（開機訊息、逾時請求的遲到回覆）都會被忽略。

PC → ESP32ESP32 → PC用途
PINGPONG <energy> <capacity>連線握手。開埠時 ESP32 可能重開機，Python 會重試 3 秒
REQ <id> <LABEL>OK <id> <energy>
NO <id> <energy>		申請施放。回 OK 時已經扣掉能量
REFUND <id>REFUNDED <id> <energy>
NO <id> <energy>		退回某次獲准的能量，同一個 id 只退一次
FILLPONG <energy> <capacity>補滿能量，測試用
（開機時）READY <energy> <capacity>開機訊息，Python 不依賴這行

已知限制

        
測試前要知道的事

        
    
            
  • 韌體和 Python 整合都是照協定寫的，還沒有在實體 ESP32 上跑過。單元測試也還沒在專案環境執行。
    • 
            
  • ESP32 不知道競技場的氣量和冷卻，只管自己的能量；競技場拒絕後才靠 REFUND 補回。
    • 
            
  • 如果競技場在 1.5 秒逾時之後才回報施放成功，那次會變成免費施放。正常情況下施放結果在一個 tick（約 17ms）內就會回來。
    • 
            
  • 韌體只保留最近 16 筆可退款的紀錄，太久以前的申請無法退回。
    • 
            
  • --energy-port 也接受 socket://IP:port，但目前韌體只實作 USB 序列埠，Wi-Fi 需要另外加。
